# Device vault and privacy checkpoint

This is a synthetic-data demonstration for Visit Bridge. The encryption and app lock are implemented; this is not certification for production health data. The original marker AR, portable card, model packs and external validation requirements remain retained.

## User flow

1. Close older Visit Bridge tabs and reopen the app on the same origin. A waiting service-worker update becomes active after old tabs close. Earlier tabs may retain plaintext already on their screens and cannot be retroactively cleared by the new code.
2. On first setup, enter and repeat your own 15–256 character passphrase. Do not share it. Existing legacy cards remain plaintext until setup succeeds. Setup validates, encrypts and decrypts every legacy card, compares full content, then atomically stores the vault configuration and encrypted envelopes and clears the old records. Any validation/encryption/commit failure retains the originals. Never assume encryption before the migration finishes.
3. Every reload starts locked. Unlock with the passphrase; wrong passphrases and damaged ciphertext do not erase data or show a partial collection. The locked screen shows no instructions or card count.
4. Dictation permission and device-saving permission are separate worker attestations for a fictional encounter. Each defaults to not recorded. Dictation cannot start without permission; declining leaves typing available. Saving cannot happen without permission; declining leaves the approved card readable without persisting it. These choices do not approve medical content or replace either worker approval gate.
5. Lock now clears the current unsaved visit, source, card arrays, selected card, proposals, dictation undo/interim text and AR snapshot. Mic/audio/AR/inference stop. Late results and pending storage work are cancelled or ignored. A transaction already committed before a lock retains only its encrypted saved copy. Lock is available inside AR too.
6. Inactivity locks after five minutes. Backgrounding immediately stops media and locks after one minute; a deadline check also catches suspended timers when returning. Pagehide and restored back/forward cache pages lock. Activity does not allow late cancelled work to repopulate a session. A lock broadcast contains only its type and locks other upgraded tabs on the same origin; keys are never shared. Browsers without BroadcastChannel retain per-tab locks but lack coordinated cross-tab clearing.
7. Device vault controls on Overview let the user change their passphrase by supplying the current one; this rewraps the same data key and locks all upgraded tabs. Cards do not need rewriting. Settings revision checks prevent stale tabs from writing after a change or erase.
8. Erase requires typing ERASE SAVED CARDS deliberately. It removes encrypted cards, any legacy cards and vault settings in one transaction. There is no recovery; public app/model/language caches remain installed. Individual card deletion retains its confirmation dialog. Deletion is logical browser deletion, not a guarantee of forensic erasure from disk, backups or screenshots.

## Storage and cryptography

IndexedDB database `visit-bridge` version 2 has `care-cards` (legacy), `encrypted-cards` and `vault-settings`. Version 1 clients cannot reopen it after upgrade. Upgrading the schema alone does not encrypt data; only successful vault setup/migration does.

The full approved payload is encrypted: original and final text, structured details/source spans, AI draft and provenance, translation-pack snapshot, understanding observation, permission choices and timestamps. Schema 6 carries a strict purpose-specific permission record; legacy schemas 1–5 are migrated byte-for-content-equivalent JSON without inventing decisions, approvals or understanding results. Legacy cards explicitly show that permission was not recorded. A new save requires storage permission even if the display/read-aloud/AR snapshot is valid without it.

A random 256-bit AES-GCM data key encrypts cards with fresh random 96-bit IVs and 128-bit authentication tags. Authenticated additional data binds the format, vault identity and card ID, preventing substitution across IDs/vaults. The key is wrapped with AES-GCM using a passphrase-derived key: PBKDF2-HMAC-SHA256, random 128-bit salt, 600,000 iterations. Rewrapping has a fresh salt and IV and advances the configuration revision. Card IDs, envelope sizes, format and cryptographic settings remain visible; contents and timestamps are encrypted. Card count can be inferred by someone inspecting storage, although the locked app does not display it.

The imported data key is nonextractable and held only in the current page session. Raw key and encoding buffers are overwritten where possible; application references are released at lock. JavaScript strings, browser/OS internals and engine memory cannot be reliably wiped by this app. No raw passphrase or unwrapped key is saved to IndexedDB, localStorage, caches or a backend. The public shell and downloadable packs are cached separately from cards.

PBKDF2 is not memory-hard. A weak passphrase may be guessed offline from a copied vault. A person with the passphrase can unlock; someone using an already unlocked browser can read the rendered card. XSS, malicious extensions, malware, device compromise, screen capture and shared credentials remain risks. CSP, escaping and short sessions help but do not prove protection against them. Forgotten passphrases have no recovery; browser eviction/clearing loses cards. No cloud backup, remote wipe, revocation or institutional device management is implemented. Production use requires qualified security review and a context-specific consent/device-management process.

References for the design: [OWASP cryptographic storage](https://cheatsheetseries.owasp.org/cheatsheets/Cryptographic_Storage_Cheat_Sheet.html), [OWASP HTML5 security](https://cheatsheetseries.owasp.org/cheatsheets/HTML5_Security_Cheat_Sheet.html) and [Web Cryptography specification](https://www.w3.org/TR/WebCryptoAPI/). These references do not endorse this prototype.

## Verification and limits

67 automated tests pass, including full-payload authentication, random nonces, wrong-passphrase and tampering refusal, nonextractable keys, rewrapping, schema 1–5 lossless migration, failed commits preserving originals, stale-tab write fencing, encryption/unlock cancellation, consent admission, timer policy and speech-memory clearing. The storage unit tests use a controllable in-memory adapter to inject failed commits; they do not pretend to be native IndexedDB.

The additional browser runner uses actual IndexedDB/Web Crypto on a disposable origin with synthetic records. It checks real version-1-to-2 upgrade and old-client fencing, migration, ciphertext at rest, authenticated reopening, encrypted writes, stale configuration, pending-write cancellation, deletion, explicit erase and invalid migration preservation. Run with `QA_VAULT=1 PORT=5177 node scripts/serve.mjs` and open `/tests/browser-vault.html` only on a disposable origin. The runner deliberately replaces that origin's test database; never enable it against an origin holding user data. Default server routes exclude this runner, and the service worker does not cache it.

Browser UI verification covered wrong/correct passphrases, declined dictation with the typed path, source/final approvals, declined saving while showing a card, permission-enabled encrypted saving, saved reopening, AR Lock now clearing its preview, cross-tab broadcast locking, and a 390×844 locked screen without horizontal overflow or card text. With the server on the test origin stopped, the cached app reloaded locked, unlocked and reopened encrypted cards. That is an application-server outage test, not a physical airplane-mode or target-phone test. Physical timers/media, actual low-memory device costs, microphone hardware, offline AR runtime and full device/network/security validation remain outstanding.
